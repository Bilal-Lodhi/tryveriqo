# Release notes — v0.1.0 candidate

**Status: prepared, not published.** No tag, no GitHub release, no remote, no
hosted instance.

## What this is

The first release candidate of the Assessment Integrity Platform: an
open-source, self-hostable service for generating online assessments and giving
reviewers evidence-based integrity signals about how candidates completed them.

## Highlights

* **Assessment generation** from a single description, producing a structured
  suite with roles, competencies, problems, hidden test cases, scoring formulas
  and per-problem integrity thresholds.
* **Candidate sessions** with short-lived, candidate-scoped credentials and a
  full lifecycle (`in_progress → submitted → flagged → evaluated`, or
  `terminated`).
* **Telemetry ingestion** for nine event types, with duplicate suppression and
  post-restart recovery.
* **Integrity analysis** producing an advisory score, structured flags, a
  similarity report and behavioural anomalies — deliberately described as
  signals, never as findings.
* **A reviewer console** with the submission beside the candidate's timeline.
* **Security by default**: fail-closed production startup, no default credential,
  an explicit CORS allow-list, and a token-guarded tool surface.
* **A self-hostable stack**: `cp .env.example .env && docker compose up --build`.

## Known gaps

1. **No live provider verification.** Generation is exercised only through
   recorded parser fixtures and a stub at the provider boundary. No API key was
   available in the extraction environment. **Publish nothing until one real call
   has been made and recorded.**
2. No live session streaming. The API is request/response and the console
   refreshes on demand.
3. Reference completions for similarity analysis are supplied by the caller;
   there is no external corpus.
4. The console's operator token is compiled into its bundle.
5. Single shared operator credential: no per-reviewer identity, no RBAC, no
   access log.
6. Candidate registration is open: any caller can register any `candidateId`.
   Candidate tokens scope telemetry submission, not eligibility.
7. No provider abstraction beyond the single Gemini implementation. The boundary
   exists; a second provider has deliberately not been added.

## Pre-publication checklist

Before this becomes a release:

- [ ] Make one real assessment-generation call against a live provider and record
      provider, model, latency, parser outcome and persistence.
- [ ] Record that result in `docs/release/verification.md`.
- [ ] Re-run the full local verification suite on the release commit.
- [ ] Confirm no secret is tracked: credential guard plus gitleaks over full
      history.
- [ ] Confirm the retired-identifier census is clean.
- [ ] Decide the product name (currently a placeholder).
- [ ] Create the remote, push, tag `v0.1.0`, and publish — each as a separate,
      explicitly authorised step.

## Prohibited in this phase

No GitHub repository, no remote, no push, no tag, no published release, no
purchased domain, no final brand decision, and no public hosted instance. Those
are all separate decisions that require separate authorisation.
